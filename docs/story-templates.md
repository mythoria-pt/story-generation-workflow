# Story templates and optional guidance

The WebApp owns recipes, user choices, fallback questions and authentication. Its global flag and author database opt-in must both be enabled for new guided requests; the opt-in defaults false and is exposed as a boolean through profile GET/PATCH. Disabling either pauses stored journeys while accepted jobs remain pollable and recoverable; standard creation stays available. Request-specific gates still apply. SGW offers an optional stateless guide using the configured text gateway. No story is created and no user credits are charged by guidance.

`POST /ai/text/story-guide` requires the existing service API key and `STORY_TEMPLATES_ENABLED=true` (default false). The trusted WebApp supplies the current author UUID, guide-session UUID, nonnegative revision, one of the five UI locales, a versioned template (`id`, positive integer `version`, `premise`, `mode`), confirmed `answers`, optional `previousQuestions`, preferences and contribution text. Raw media paths and arbitrary URLs are not accepted. The proxy must scope any media extraction to the authenticated author.

The response is `{revision, source: 'ai', question}`. A question has `id`, `text`, three or four `{id,label,value}` choices, and a nullable `suggestedChoiceId`. Null question means the guide is finished. Output is schema-validated; memory mode never preselects a choice. Earlier questions, including skipped questions, are context only. Confirmed answers remain distinct from proposals.

SGW returns 400 for invalid requests, 404 while disabled, 429 for exhausted quota, 504 for the ten-second generation deadline, and 502 for unavailable/invalid model output. The WebApp supplies localized authored fallback questions and allows users to continue. It must ignore stale revisions and cancel obsolete requests. Abort signals reach both provider adapters; private calls omit content from logs/token telemetry and disable OpenAI response storage. Existing token accounting uses action `story_enhancement`, correlation `guide:<uuid>` and operation `story_guide`.

Workflows DB quota counters admit at most nine calls per author/journey and thirty per author/UTC day. Both counters update atomically; failed/timed-out admitted calls still count. The additive migration `0008_violet_proudstar.sql` was generated with `npm run workflows-db:generate` and applied through the authorized migration process on 2026-09-19. New environments require it before activation. Routine local validation must not apply migrations or run fixtures against the production-shared database. Counters store no answers or prompts; journey counters persist to prevent quota reset by day rollover.

Both story-structure endpoints accept optional `storyPreferences` (canonical target-audience, novel-style and graphical-style enums plus tone) and `factuality: 'memory'`. Preferences are included in extraction input and deterministically override extracted fields before persistence. Tone and memory constraints persist in additional requests and the input snapshot for subsequent generation. Omitting these fields preserves the old contract. The paid generation/credit workflow is unchanged.

The pt-PT guide can additionally receive `photoAnswers: true`. Only those requests may return optional `photoTarget: 'protagonist'` on a question about the single protagonist's visual identity; all other questions omit it or use null. Other locales reject the opt-in. Photos remain in the authenticated WebApp upload flow, never in the stateless guide request. Pending uploads and subject choices are proposals until the author confirms the answer.

Both structure endpoints accept optional `characterReferences` with at most one item: `{questionId, question, answer, imageObjectPath, sourceCharacterIndex, targetRole: 'protagonist'}`. The path must also appear in `imageObjectPaths`, and the request locale must be pt-PT. The WebApp supplies confirmed answers only, including neutral text for a photo-only answer. Ownership-checked relocation resolves the original submitted path to its durable story path. SGW validates the selected index against persisted server photo metadata and prepares that subject's crop before calling the structure model. Missing subjects, non-photos and invalid crops fail visibly.

Character-only photos are excluded from generic image metadata, OCR, background interpretation, cover-photo selection and heuristic character mapping. Only the selected subject's appearance and the confirmed answer inform the protagonist. Photos never establish biographical facts or events, including in memory mode. The model must return exactly one protagonist; SGW binds its appearance and selected crop explicitly, creates a new character rather than modifying a library character, and requires the photo and story association to persist. That character's JPEG `photoGcsUri` then uses the existing scene-character reference pipeline for covers and chapter illustrations. The original full photograph is not a cover/background reference. The confirmed association persists in the story input manifest and participates in the durable request hash. Omitting `characterReferences` retains the existing media behavior. No database migration or paid generation change is required.

## Retrying story structuring

`POST /api/jobs/story-structure` accepts optional `structureRequestId` (UUID). The WebApp persists this ID and the exact submitted payload before requesting work. The request ID is also the durable job ID. An atomic insert in `structure_jobs` binds it to a story and SHA-256 input hash; duplicates return the same job with `duplicate: true` and never relaunch work. A different story or payload with that ID returns 409. Omitted IDs retain the legacy in-memory job path.

`GET /api/jobs/:jobId` can read the durable result from any instance and includes `job.metadata.storyId` for proxy ownership validation. Pending/processing records expire after five minutes and polling marks them failed. Completed results persist; request IDs are never automatically reclaimed. Rotate the ID only after known terminal failure or confirmed changed input. Additive migration `0009_smooth_ink.sql` was applied on 2026-09-19; new environments require it before this request option is enabled.

All structure callers share a per-story PostgreSQL session advisory lock. Each process admits up to four lock holders/waiters using the existing fifteen-connection story pool, leaving capacity for the worker's ordinary service queries. Acquisition uses try-lock polling bounded by the deadline. The deadline aborts provider calls and guards subsequent mutation boundaries. Crucially, the lock remains held until the underlying service settles, even after timeout; a later retry cannot race a still-running worker. A crashed process releases its database session lock. Do not replace this with a Promise.race that releases the lock while mutations continue.

Media recovery verifies author ownership before reading paths, accepts a staging source or the same-story destination already moved by the previous attempt, and only returns a destination that really exists. Keep original submitted paths when replaying a request ID. The WebApp must not assume relocation happened merely because a job was accepted. Story input snapshots include confirmed preferences and factuality instructions.

Tests cover duplicate/conflicting identities, persisted polling metadata, expired-worker lock retention, bounded lock acquisition, moved-input recovery and ownership/missing-input failures. Actual cross-instance PostgreSQL contention and process termination recovery are not proven by mocked tests and require an isolated database run.
